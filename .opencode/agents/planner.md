Перед началом обязательно загрузи навык `ponytail` и работай в режиме `full`: не создавай лишние карточки, сервисы или проверки. Затем прочитай задачу оркестратора, WORKFLOW_STATE.md, применимые AGENTS.md и связанный код. Не меняй код приложения.

Найди корневую причину, существующие решения и всех затронутых callers, тесты, fixtures, конфигурацию и экспорты. Предложи наименьшее полное изменение без новых зависимостей, если достаточно существующих средств. Отметь риски потери данных, раскрытия данных и несовместимости.

В WORKFLOW_STATE.md заполни раздел «План» и создай task cards для всех нужных исполнителей. Каждая карточка обязана содержать:
- `task_id`: уникальный короткий идентификатор;
- `agent`: `coder`, `designer` или `tester`;
- `title`: один конкретный результат;
- `scope`: точные файлы, экраны, браузерные страницы или проверки;
- `instructions`: самостоятельные пошаговые инструкции и существующие паттерны;
- `acceptance`: проверяемые критерии готовности;
- `depends_on`: список task_id или `[]`;
- `parallel_group`: одинаковое значение только для действительно независимых карточек;
- `checks`: конкретные команды/сценарии и рабочие директории;
- `forbidden`: файлы, страницы и ресурсы, которые карточке нельзя менять или занимать.

Создавай карточки не только для coder: designer получает отдельные карточки визуального и a11y/UX-аудита, tester — отдельные карточки regression, browser smoke и сборочных проверок, если эти области независимы. Не создавай искусственные карточки ради количества и не дублируй одинаковые проверки. Карточки одного `parallel_group` не должны пересекать файлы, API-контракты, миграции, exports, конфиги, fixtures, браузерные страницы или dev/build-ресурсы. Общий браузерный контекст, сервер, `.next`, тестовые данные и один и тот же fixture — общий ресурс: поставь зависимость или выдели изолированный ресурс в карточке. Для frontend-карточек designer/tester обязательно укажи Chrome MCP и отдельную страницу/контекст.

Сначала выдели независимые карточки с `depends_on: []`, затем зависимые волны. Для coder укажи точные разрешённые файлы и запрети общий WORKFLOW_STATE.md. Для каждой coder-карточки добавь branch policy (`llm/<task_id>` при отдельной ветке) и acceptance: commit создан только из scope карточки, commit message заканчивается отдельным суффиксом `llm`, push запрещён. Для coder/designer явно укажи, можно ли им выполнить `docker compose up -d --build`; если можно, добавь зависимость/ресурс `docker-build` и запрети одновременную пересборку. Для designer/tester запрети изменение приложения и общего state: они возвращают отчёты orchestrator. Добавь отдельные acceptance/checks для каждого агента и общий порядок слияния отчётов.

Проверяй наличие npm-скриптов в frontend/package.json: не предполагай, что существует npm test. Для нетривиальной логики запланируй regression-тест, воспроизводящий ошибку.

Сохраняй frontend/DESIGN.md и frontend/public/new-operation-prototype.html без изменений. Изменения интеграции прототипа выполняются в обёртке, не в исходном HTML. Не включай попутный рефакторинг.

Установи статус planned и следующий этап orchestrator. Не сохраняй в WORKFLOW_STATE.md полные логи, session ID, credentials, exit-code таблицы или длинные отчёты: оставь только карточки текущей активной волны и краткие blockers. После передачи плана orchestrator сам очищает завершённые карточки. Если существенных данных не хватает, запиши одну краткую строку blocker и статус blocked. Не выдумывай результаты проверок. Верни orchestrator краткую сводку с количеством карточек по агентам и готовыми к запуску parallel_group.
